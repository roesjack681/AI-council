## 完整软件开发需求与技术设计文档

**文档版本：** V1.0  
**产品类型：** Chrome 浏览器扩展  
**开发语言：** TypeScript  
**前端框架：** Vue 3

# 第一章：项目概述

## 1.1 项目背景

用户在日常使用 AI 时，通常需要在多个模型之间反复复制问题和答案。

例如：

1. 在 ChatGPT 提出一个技术问题。
2. 等待 GPT 输出解决方案。
3. 复制 GPT 的方案。
4. 打开 Gemini，将 GPT 的方案交给 Gemini 审查。
5. 复制 Gemini 的质疑。
6. 返回 GPT，让 GPT 回应。
7. 再将 GPT 的回应交给 Gemini。
8. 重复上述过程，直到多个模型形成一致意见。

这种工作方式存在以下问题：

- 需要频繁切换网页。
- 需要反复复制和粘贴。
- 容易遗漏上下文。
- 容易混淆不同模型的回答。
- 无法方便地管理多轮讨论。
- 无法自动判断是否真正解决争议。
- 需要用户持续参与整个过程。

本项目的目标就是将这一过程交给浏览器插件管理。

## 1.2 产品核心目标

开发一个 Chrome 浏览器扩展。

用户只需要：

1. 打开 ChatGPT、Gemini、Claude 等 AI 网页。
2. 登录自己的账号。
3. 在任意一个参与的 AI 网页中提出问题。
4. 点击发送。

随后系统负责：

- 识别新讨论任务。
- 管理原始问题。
- 管理各个模型的讨论会话。
- 获取平台允许自动处理的模型回复。
- 将模型回复交给其他参与模型。
- 生成交叉审查提示词。
- 组织模型自由讨论。
- 管理争议和解决状态。
- 判断是否达成共识。
- 生成最终报告。
- 通知用户讨论完成。

正常运行期间不要求用户复制、粘贴、切换标签页或确认每一条消息。

**重要约束：** 无人值守能力必须以每个平台明确允许的交互方式为前提。
## 1.3 核心原则

1. 不使用 OpenAI API。
2. 不使用 Gemini API。
3. 不使用 Claude API。
4. 不要求用户提供账号密码。

9. 所有讨论数据默认保存在本地。

# 第三章：系统总体架构

## 3.1 架构设计

系统采用 Chrome Extension Manifest V3 架构。

整体分为六个层次：

1. 浏览器交互层。
2. 模型适配层。
3. 消息协调层。
4. 自由讨论引擎。
5. 共识判断引擎。
6. 本地存储层。

架构关系：

```text
                  用户
                   |
                   v
             Chrome 浏览器
                   |
                   v
          AI Council 扩展界面
                   |
                   v
            任务管理中心
                   |
        +----------+----------+
        |          |          |
        v          v          v
    GPT适配器  Gemini适配器  Claude适配器
        |          |          |
        v          v          v
    GPT网页     Gemini网页    Claude网页
        |          |          |
        +----------+----------+
                   |
                   v
              消息协调器
                   |
          +--------+--------+
          |                 |
          v                 v
      讨论引擎          争议管理引擎
          |                 |
          +--------+--------+
                   |
                   v
               共识引擎
                   |
                   v
               报告生成器
                   |
                   v
              IndexedDB
                   |
                   v
               最终结果
```

上述模型适配器只允许实现各平台授权的交互能力。对于不允许程序化提取输出的平台，适配器必须报告不可用，不得用 DOM 抓取、私有接口或其他规避方式替代。

## 3.2 技术选型

| 模块 | 技术 |
|---|---|
| 浏览器插件 | Chrome Extension MV3 |
| 前端框架 | Vue 3 |
| 编程语言 | TypeScript |
| 构建工具 | Vite |
| UI 组件 | Naive UI |
| 状态管理 | Pinia |
| 本地数据库 | IndexedDB |
| 数据封装 | Dexie.js |
| 浏览器消息通信 | Chrome Runtime Messaging |
| 标签管理 | Chrome Tabs API |
| 侧边栏 | Chrome Side Panel API |
| 后台调度 | Extension Service Worker |
| 任务恢复 | IndexedDB + chrome.alarms |
| 数据验证 | Zod |
| 测试 | Vitest + Playwright |

不需要：

- FastAPI。
- Spring Boot。
- MySQL。
- Redis。
- 独立云服务器。
- 模型 API Key。

所有任务协调和数据管理在本地完成。

## 3.3 浏览器运行条件

必须明确：

1. Chrome 浏览器需要保持运行。
2. 电脑需要保持开机。
3. 系统不能进入导致浏览器停止工作的休眠状态。
4. 参与的 AI 网页必须保持有效登录状态。
5. 模型网站需要能够正常访问。
6. 浏览器扩展需要具有所需且经过用户授权的权限。

Chrome MV3 Service Worker 可能被系统挂起，因此不能将内存变量作为任务唯一状态。

所有重要状态必须持久化。

浏览器重新启动后，需要能够恢复之前的讨论任务。

浏览器关闭、电脑关机或网络断开时，不保证模型讨论能够继续运行。

# 第四章：浏览器插件设计

## 4.1 插件结构

采用 Side Panel 作为主要交互界面。

插件分为：

### A. Background Service Worker

负责：

- 维护讨论任务状态。
- 管理标签页。
- 接收模块消息。
- 维护任务调度。
- 保存运行状态。
- 检测任务超时。
- 恢复中断任务。

不得依赖 Service Worker 的常驻运行。

### B. Side Panel

负责：

- 创建讨论任务。
- 管理参与模型。
- 显示讨论过程。
- 显示争议。
- 显示共识状态。
- 显示最终报告。
- 暂停和恢复任务。

### C. Content Script / 页面适配层

负责平台授权范围内的网页交互。

设计为插件式适配器。

每个适配器必须声明：

- 平台名称。
- 适配器版本。
- 支持的网页地址。
- 允许的读取能力。
- 允许的发送能力。
- 登录状态检测能力。
- 回答完成状态检测能力。
- 是否支持无人值守运行。
- 失败处理方式。

不能假设所有平台具有相同的网页结构和交互方式。

### D. Discussion Engine

负责讨论流程。

### E. Consensus Engine

负责共识判断。

### F. Database Layer

负责所有数据持久化。

## 4.2 页面设计

插件需要五个主要页面。

1. 工作台。
2. 参与模型管理。
3. 实时讨论。
4. 争议管理。
5. 最终报告。

# 第五章：参与者管理模块

## 5.1 参与者数据结构

每个参与者具有以下属性：

```typescript
interface Participant {
  id: string;

  name: string;

  platform:
    | "chatgpt"
    | "gemini"
    | "claude"
    | "custom";

  websiteUrl: string;

  enabled: boolean;

  adapterId: string;

  adapterVersion: string;

  capabilities: {
    canReadOutput: boolean;
    canSubmitMessage: boolean;
    canDetectCompletion: boolean;
    unattendedAllowed: boolean;
  };

  status:
    | "available"
    | "logged_out"
    | "unsupported"
    | "restricted"
    | "error";

  createdAt: number;
  updatedAt: number;
}
```

能力字段必须由适配器的真实检查结果决定，不能通过配置文件强行声明支持。

## 5.2 参与者管理功能

- 添加参与者。
- 删除参与者。
- 启用和停用参与者。
- 打开对应网页。
- 检查网页可用性。
- 检查适配器能力。
- 显示不可用原因。
- 显示是否满足无人值守条件。

## 5.3 参与者可用性检查

创建任务之前，必须检查参与者是否满足运行条件。

检查内容：

1. 对应网页是否打开。
2. 网页是否能够正常访问。
3. 用户是否已经登录。
4. 适配器是否正常。
5. 平台是否允许所需的自动交互。
6. 是否能够安全地获取消息。
7. 是否能够提交消息。
8. 是否能够检测回答完成。

只要有一个关键条件不满足，就不能将该模型标记为无人值守可用。

# 第六章：讨论任务管理模块

## 6.1 任务创建

讨论任务至少包含：

- 任务 ID。
- 任务标题。
- 原始问题。
- 问题背景。
- 已知条件。
- 必须遵守的约束。
- 期望结果。
- 参与模型。
- 最大讨论轮数。
- 共识规则。
- 创建时间。
- 当前状态。

数据结构：

```typescript
interface Discussion {
  id: string;

  title: string;

  originalQuestion: string;

  context: string;

  constraints: string[];

  expectedOutput: string;

  participantIds: string[];

  mode: "free";

  maxRounds: number;

  currentRound: number;

  status:
    | "created"
    | "initializing"
    | "discussing"
    | "consensus_check"
    | "completed"
    | "unresolved"
    | "paused"
    | "failed";

  createdAt: number;

  updatedAt: number;
}
```

## 6.2 任务发起方式

支持任意参与模型作为初始发起入口。

例如：

用户在 GPT 网页提出问题并发送。

系统在平台允许的情况下，将该问题识别为新的讨论任务。

其他模型随后加入。

也支持用户在 Gemini 或 Claude 网页发起任务。

系统需要区分：

- 用户原始问题。
- 模型讨论消息。
- 模型追问。
- 模型修改方案。

不能把模型之间的讨论消息误认为用户创建的新任务。

## 6.3 任务上下文锁定

任务创建后，原始问题必须永久保留。

后续模型不能覆盖原始问题。

讨论过程中的修改只影响方案，不影响任务原始要求。

每个模型都必须能够获得：

1. 原始问题。
2. 原始约束。
3. 当前方案。
4. 历史讨论摘要。
5. 尚未解决的争议。
6. 最新模型发言。

# 第七章：消息管理模块

## 7.1 消息类型

系统支持以下消息类型：

| 类型 | 说明 |
|---|---|
| INITIAL_ANSWER | 模型初始回答 |
| REVIEW | 审查其他模型方案 |
| OBJECTION | 提出质疑 |
| RESPONSE | 回应质疑 |
| REVISION | 修改方案 |
| AGREEMENT | 表达认可 |
| DISAGREEMENT | 表达反对 |
| FACT_CHECK | 事实核验 |
| FINAL_POSITION | 最终立场 |

## 7.2 消息结构

```typescript
interface DiscussionMessage {
  id: string;

  discussionId: string;

  roundId: string;

  participantId: string;

  type: string;

  content: string;

  structuredData?: object;

  replyTo?: string;

  relatedClaimIds: string[];

  relatedObjectionIds: string[];

  status:
    | "pending"
    | "delivered"
    | "received"
    | "failed";

  createdAt: number;
}
```

每条消息都必须具有唯一 ID。

消息不能因为重新发送而产生重复讨论记录。

## 7.3 消息交接机制

系统采用任务队列。

每条消息必须经过以下流程：

```text
消息生成
   |
   v
消息持久化
   |
   v
检查目标模型能力
   |
   v
加入待发送队列
   |
   v
发送
   |
   v
等待响应
   |
   v
记录完整响应
   |
   v
更新讨论状态
```

发送失败时：

- 记录失败原因。
- 进行有限次数重试。
- 避免重复发送。
- 超过重试次数后标记失败。
- 不得把失败消息视为模型已阅读。

消息发送必须具备幂等性。

# 第八章：多模型自由讨论引擎

这是整个项目的核心模块。

## 8.1 讨论原则

本系统不采用固定的 GPT → Gemini → Claude 轮流发言模式。

采用自由讨论。

每个模型可以：

- 主动反驳其他模型。
- 补充其他模型的方案。
- 指出逻辑错误。
- 提出新方案。
- 修改自己的方案。
- 对其他模型提出质疑。
- 对合理观点表示认可。
- 对无法验证的内容保留意见。

所有模型共享一份统一的讨论上下文。

## 8.2 第一阶段：独立回答

任务启动后，所有参与模型分别收到相同的原始问题。

提示词：

```text
你现在是 AI Council 的独立技术评审成员。

请独立解决以下问题。

在初始阶段：
1. 不参考其他模型的观点。
2. 独立分析需求。
3. 提出完整解决方案。
4. 说明关键技术选择。
5. 说明设计依据。
6. 指出潜在风险。
7. 列出无法确定的问题。

不要为了迎合其他模型而给出结论。

原始任务：
{{original_question}}

已知条件：
{{context}}

必须满足的约束：
{{constraints}}
```

所有模型完成独立回答后，进入自由讨论。

## 8.3 第二阶段：交叉审查

系统向每个模型提供：

- 原始问题。
- 所有模型的初始答案。
- 当前公共讨论摘要。

要求模型自主分析：

1. 哪些方案是合理的。
2. 哪些方案存在错误。
3. 哪些方案存在遗漏。
4. 哪些技术判断缺少依据。
5. 哪些方案值得吸收。
6. 是否有更好的方案。

## 8.4 第三阶段：自由讨论

提示词：

```text
你现在参与 AI Council 多模型自由讨论。

原始问题：
{{original_question}}

其他模型的方案：
{{all_model_answers}}

历史讨论记录：
{{discussion_history}}

当前争议：
{{open_objections}}

请根据实际情况自由发表意见。

你可以：

1. 反驳其他模型的观点。
2. 支持其他模型的观点。
3. 补充其他模型遗漏的内容。
4. 提出新的解决方案。
5. 修改自己的方案。
6. 对其他模型的质疑逐条回应。
7. 承认自己之前的错误。
8. 对无法验证的问题明确保留意见。

禁止为了达成一致而无条件认可其他模型。

如果你认为某个方案确实存在问题，
必须明确指出问题和依据。

如果你认可其他模型的方案，
需要说明认可的具体内容和原因。

请区分事实、推测、假设和个人判断。
```

## 8.5 自由发言调度

系统不应要求每个模型每轮都机械输出一份完整方案。

采用事件驱动讨论。

当出现以下事件时，触发新讨论：

- 出现新的重大质疑。
- 某个模型提出新的方案。
- 某个模型修改关键结论。
- 某个争议得到回应。
- 某个事实核验结果出现。
- 需要其他模型确认某项结论。

系统根据未解决问题选择需要回应的模型。

如果一个模型已经回应某项质疑，不应重复要求它再次回答相同问题。

## 8.6 公共上下文管理

每次讨论完成后，生成一份公共摘要。

摘要必须包含：

```text
原始任务：
当前主要方案：
所有模型认可的观点：
存在分歧的观点：
已解决的争议：
未解决的争议：
新增事实：
新增假设：
方案修改记录：
下一步需要讨论的问题：
```

注意：

摘要只用于减少上下文长度，不能删除原始消息。

所有模型都应该能够查看完整历史记录。

# 第九章：争议管理模块

## 9.1 争议数据结构

```typescript
interface Objection {
  id: string;

  discussionId: string;

  title: string;

  description: string;

  sourceParticipantId: string;

  targetParticipantIds: string[];

  relatedClaimId: string;

  severity:
    | "minor"
    | "major"
    | "critical";

  status:
    | "open"
    | "responding"
    | "resolved"
    | "unresolved"
    | "disputed";

  evidence: string[];

  resolution?: string;

  createdAt: number;

  resolvedAt?: number;
}
```

## 9.2 争议严重程度

### Minor

不影响核心方案的小问题。

### Major

会影响方案实施或部分关键结论的问题。

### Critical

会导致整体方案错误、不可实施或存在严重风险的问题。

## 9.3 争议解决流程

```text
模型提出质疑
     |
     v
创建争议记录
     |
     v
确定受影响结论
     |
     v
通知相关模型回应
     |
     v
收集回应与证据
     |
     v
其他模型复核
     |
     v
更新争议状态
     |
     +---- 已解决
     |
     +---- 仍然存在分歧
     |
     +---- 证据不足
```

## 9.4 争议解决规则

以下情况可以标记为已解决：

- 原提出者撤回质疑并说明原因。
- 相关模型通过充分证据解决问题。
- 所有相关模型认可修订后的结论。
- 原方案被替换，争议不再影响最终结果。

不能因为某个模型简单回复“我同意”就自动关闭重大争议。

# 第十章：共识判断引擎

## 10.1 共识目标

系统需要判断多个模型是否真正形成一致意见。

不允许使用简单多数投票。

不允许仅根据模型输出中的“我同意”判断共识。

## 10.2 模型立场

每个模型对每项核心结论必须有独立立场。

```typescript
type ConsensusPosition =
  | "AGREE"
  | "CONDITIONAL"
  | "DISAGREE"
  | "UNCERTAIN"
  | "ABSTAIN";
```

说明：

AGREE：认可结论。

CONDITIONAL：在指定条件满足时认可。

DISAGREE：明确反对。

UNCERTAIN：无法判断。

ABSTAIN：暂不表态。

## 10.3 共识通过条件

默认采用严格共识机制：

1. 所有有效参与模型均完成最终表态。
2. 所有核心结论均获得全体模型认可。
3. 不存在未解决的 Major 或 Critical 争议。
4. 所有 Conditional 条件均已满足。
5. 关键事实已经核验。
6. 连续两次共识检查没有新的重大分歧。

全部满足才允许标记为 CONSENSUS_REACHED。

注意：

模型之间的一致意见不等于客观事实正确。

事实核验必须单独记录。

## 10.4 核心结论管理

每个结论都必须独立编号。

例如：

```text
CLAIM-001
结论：采用8路视频输入架构。

CLAIM-002
结论：每路视频采集帧率为30 FPS。

CLAIM-003
结论：目标检测频率为每路15 FPS。

CLAIM-004
结论：推理服务器满足实际吞吐要求。
```

每个模型需要对每条核心结论单独表态。

不能将所有观点合并为一个笼统的同意或反对。

## 10.5 共识检测数据结构

```typescript
interface ConsensusResult {
  discussionId: string;

  reached: boolean;

  participantCompletion: boolean;

  coreClaimsAccepted: boolean;

  unresolvedMajorObjections: number;

  unresolvedCriticalObjections: number;

  unresolvedConditions: number;

  unverifiedCriticalFacts: number;

  stableRounds: number;

  reasons: string[];

  checkedAt: number;
}
```

## 10.6 共识判断逻辑

共识判断必须由确定性规则引擎执行。

模型负责提出观点和立场。

程序负责统计状态和检查条件。

禁止让某一个模型仅凭自身判断决定所有模型已经达成共识。

## 10.7 最大讨论轮数

默认设置：

- 最大讨论轮数：10。
- 连续稳定轮数：2。
- 消息重试次数：3。
- 单个模型等待时间：根据模型网页响应情况配置。
- 超过最大轮数：标记为 UNRESOLVED。

讨论无法达成共识时，不允许无限循环。

输出未达成共识报告，明确列出所有分歧。

# 第十一章：事实核验模块

事实核验必须与模型之间的意见交换分开。

系统需要识别：

- 事实。
- 假设。
- 推测。
- 计算结果。
- 主观建议。
- 尚未验证的结论。

例如：

GPT：某款工业相机支持800万像素、120 FPS。

Gemini：我同意。

Claude：我也同意。

不能因为三个模型都同意就认为该参数正确。

需要核对：

1. 官方产品规格书。
2. 官方技术文档。
3. 实际接口带宽。
4. 传感器分辨率。
5. 实际工作模式。
6. 是否能够同时达到目标帧率和分辨率。

事实核验模块 V1.0 只负责保存证据、来源和核验状态。

可以先支持用户提供的文档及本地计算验证。

不允许未经授权自动访问外部网站。

核验状态：

- VERIFIED：有可靠证据支持。
- CONTRADICTED：证据与结论冲突。
- UNVERIFIED：尚未核实。
- INSUFFICIENT：证据不足。
- NOT_APPLICABLE：不适用。

关键事实未验证时，不得标记为完全验证的最终共识。

# 第十二章：任务状态机

## 12.1 任务状态

```typescript
type DiscussionStatus =
  | "CREATED"
  | "INITIALIZING"
  | "INITIAL_ANSWERS"
  | "FREE_DISCUSSION"
  | "OBJECTION_REVIEW"
  | "CONSENSUS_CHECK"
  | "FINALIZING"
  | "COMPLETED"
  | "UNRESOLVED"
  | "PAUSED"
  | "FAILED";
```

## 12.2 状态流转

```text
CREATED
   |
   v
INITIALIZING
   |
   v
INITIAL_ANSWERS
   |
   v
FREE_DISCUSSION
   |
   v
OBJECTION_REVIEW
   |
   v
CONSENSUS_CHECK
   |
   +---- 达成共识 ----> FINALIZING
   |                       |
   |                       v
   |                   COMPLETED
   |
   +---- 未达成共识 ----> FREE_DISCUSSION
   |
   +---- 超过最大轮数 --> UNRESOLVED
   |
   +---- 用户暂停 ------> PAUSED
   |
   +---- 严重故障 ------> FAILED
```

## 12.3 任务恢复

任务中断后必须恢复：

- 当前讨论轮数。
- 已完成的模型回答。
- 待处理消息。
- 尚未解决的争议。
- 每个模型当前立场。
- 上一次共识检查结果。
- 当前任务状态。

恢复后不得重新执行已经成功完成的消息发送。

# 第十三章：异常处理

必须实现以下异常情况。

## 13.1 模型网页未登录

处理：

- 将模型状态标记为 LOGGED_OUT。
- 暂停依赖该模型的交接。
- 保留讨论数据。
- 不自动尝试重新登录。
- 等待用户处理。

## 13.2 模型网页不可用

处理：

- 标记模型为 UNAVAILABLE。
- 保留现有讨论记录。
- 暂停或终止依赖该模型的任务。
- 不得自动假装该模型已经回复。

## 13.3 模型回答超时

处理：

- 记录等待开始时间。
- 超过配置时间标记 TIMEOUT。
- 根据策略有限重试。
- 超过最大重试次数后暂停相关任务。

## 13.4 模型重复回答

通过消息 ID 和任务 ID 去重。

重复消息不得被当成新的观点。

## 13.5 模型回答格式错误

允许模型返回普通自然语言。

如果需要结构化数据，要求模型重新整理。

如果仍然无法解析：

- 保存原始内容。
- 标记 PARSE_FAILED。
- 不得丢弃原始回答。
- 不得自动生成虚假的结构化数据。

## 13.6 浏览器崩溃

使用 IndexedDB 恢复任务。

恢复时重新检查模型可用性。

## 13.7 讨论无限循环

设置：

- 最大讨论轮数。
- 相同质疑去重。
- 相同观点重复检测。
- 无有效信息消息检测。
- 最大连续无进展轮数。

连续三轮没有有效进展时，停止自动讨论，标记为 STALLED。
